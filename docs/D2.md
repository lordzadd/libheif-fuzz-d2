# D2 — Attack Surface Analysis and Working Harness

## Track B: untrusted-input entry points

Target: vendored libheif commit 08075aebcc0d9bf7d35f900c36114b1b6e90ed7d (libheif 1.23.4). “Reachable” means the harness invokes the entry point; deeper branches may depend on input structure or an available codec.

| Entry point / parser | Untrusted input and reachability | Harness coverage |
|---|---|---|
| heif_context_read_from_memory (public API) | Fuzzer bytes are passed directly as a memory buffer. Malformed or truncated data reaches the API and its format checks; a valid ftyp is not required to call it. | file_fuzzer, api_fuzzer, tile_fuzzer, sequence_fuzzer |
| ISOBMFF box parser and item/property/extent parsing | The same bytes flow into box parsing. Deeper item/property paths need usable lengths, references, and extents; these are input-dependent conditions, not API guards. | Through the memory API in file_fuzzer, api_fuzzer, tile_fuzzer, sequence_fuzzer |
| File-type probes: heif_check_filetype, heif_main_brand, heif_get_file_mime_type | Raw bytes and the supplied length are passed to probes before the memory-read call; no valid container is required to call them. | file_fuzzer; tile_fuzzer calls heif_check_filetype |
| Primary-image handle and decode | Reached only if parsing succeeds and a primary handle is available. Decoding further requires a usable decoder. Compressed payload and image metadata are input-controlled; codec coverage depends on build configuration and valid image structure. | file_fuzzer; related API paths are conditional |
| Tile/grid decoding | Grid and tile descriptions, references, and extents come from input. Decoding requires parsed grid metadata and supported tile payloads. | tile_fuzzer; conditions are input-dependent |
| Sequence/track parsing and decode | Track boxes and sample tables come from input. Decode requires a parseable sequence and supported sample data. | sequence_fuzzer; conditions are input-dependent |
| Direct box parser | Input is passed directly to an internal box parser; a complete HEIF container or top-level ftyp is not a precondition. | box_fuzzer |
| Color conversion | The target constructs synthetic image planes and conversion parameters from fuzzer bytes. This is a separate input path, not a parser reached through the memory API. | color_conversion_fuzzer |
| Encoder API | The target derives encoder options and image content from fuzzer bytes and calls encoding APIs. This is separate from input-file parsing. | encoder_fuzzer |

The seven targets are upstream libheif fuzz targets. The memory-API rows above exercise that file parsing path. Building or invoking a target does not mean every conditional parser or codec branch is exercised.

## Reproducible harness

From a clean clone, run:

    git clone https://github.com/lordzadd/libheif-fuzz-d2.git
    cd libheif-fuzz-d2
    python3 harness/run.py

The runner builds all seven targets and runs each with 1,000 libFuzzer executions by default. Set FUZZ_RUNS to change the fixed count, for example FUZZ_RUNS=10000 python3 harness/run.py. Each run gets a fresh copied seed corpus and a timestamped output directory under results/. It writes a CSV and JSON summary with inputs executed, crashes, exit status, and failures. It exits nonzero if a target fails, times out, or provides no execution statistics. Zero crashes is a valid numerical result.

## Build scope and prerequisites

The build uses Clang with libFuzzer, CMake, and a C++ standard library. Optional external codec libraries are disabled to reduce host-dependent configuration; the built-in uncompressed codec is enabled. This measures parsing and built-in-codec paths available in this configuration, not broad coverage of external HEVC, AV1, or JPEG codec implementations. The repository vendors libheif source and pins its upstream commit in libheif/UPSTREAM_COMMIT. Python dependencies are standard-library only; see requirements.txt.
