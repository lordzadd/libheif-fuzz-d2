**Target.** The vendored tree in `libheif/` is byte-identical to upstream commit
`08075aeb` (libheif 1.23.4, master on 9 September 2026). This was checked with
`diff -rq` against `git archive 08075aeb` of `strukturag/libheif`: no
differences.

**Harness targets.** Six upstream libFuzzer targets, unmodified:

Campaign C's environment is recorded in `results/long2a/env.txt`; the clang,
CMake, libde265, x265, libaom, zlib and brotli versions are identical to
Campaign B's `results/env.txt`. **Campaign C fuzzed the mitigated source**
(the `d3-review` branch carries M1 and M2, 7 files, +81/−15 lines). M1 and M2
only add early-return guards, so the campaign is the "after" evaluation of
Part 2 as well as a longer search. To make the null result hold for the pinned
code too, every final Campaign C corpus and every generated seed was replayed on
a build of the `d3-baseline` source (see *Before and after*).

Campaign A is the run that produced the two crash classes in Part 1. Campaign B
is a longer, independent run on a build with the codecs enabled, used to test
whether the classes are the shallow ones and whether memory-safety faults appear
in the codec-backed paths. Campaign C extends Campaign B with structured seeds
and more CPU time to search for the memory-safety violation that A and B did not
find.

**Agents and models.** Not applicable: D1 chose Track B. There is no LLM agent
and no model version to pin; the system under test is the decoder library and the
driver is libFuzzer.

# Method

## Campaign A (Part 1, `harness/campaign.py`)

Five rounds of 30 s per target, libFuzzer `-fork=2 -ignore_crashes=1`, three
targets at a time on six nominal cores. Each target keeps a private corpus that
persists across rounds. Coverage is parsed from libFuzzer status lines into
`coverage_over_time.csv`. Every artifact is reproduced with a symbolized stack,
grouped by root cause, and one representative per group is minimised with
`-minimize_crash=1` and replayed to confirm the same signature.

## Campaign B (this revision, `harness/d3/campaign.py`)

Twelve workers: `file_fuzzer` 3, `api_fuzzer` 3, `box_fuzzer` 2,
`sequence_fuzzer` 2, `tile_fuzzer` 1, `color_conversion_fuzzer` 1. Workers of
one target share a corpus directory with `-reload=1`, so they exchange inputs.

Each worker runs in chunks of at most 600 s and is restarted by a supervisor
after any exit, with a **new mutation seed per chunk**
(`seed = t0 + worker*7919 + chunk*104729`). The new seed matters: with a fixed
seed, a restart replays the same mutation stream and re-finds the same artifact
immediately.

Common flags:

```
-timeout=30 -rss_limit_mb=800 -reload=1 -print_final_stats=1
-use_value_profile=1 -artifact_prefix=results/baseline/crashes/<target>/
-dict=libheif/fuzzing/data/dictionary.txt -seed=<per chunk>
ASAN_OPTIONS=detect_leaks=0:symbolize=1
```

Crashes, OOMs, timeouts and slow units are written by libFuzzer directly into
`results/baseline/crashes/<target>/` and indexed in `crashes.csv` with a
timestamp and the chunk log that contains the sanitizer report. Every line a
worker prints is copied to `results/baseline/logs/<target>.w<k>.log` with a
wall-clock offset, so coverage over time can be rebuilt from the raw logs.

**CPU accounting.** `getrusage(RUSAGE_CHILDREN)` around the whole run, recorded
in `campaign_summary.json` as `cpu_seconds` and `cpu_hours`. Executions are the
sum of the final `stat::number_of_executed_units` over all chunks and workers.

**Corpus construction** (`harness/d3/prepare_corpus.py`). Each target starts from
the 133 upstream HEIC/AVIF fixtures in `libheif/fuzzing/data/corpus` plus
`sequence_corpus/seq_seed.heif`. `box_fuzzer`, which parses a single box with no
container, additionally receives every top-level and nested ISOBMFF box carved
out of those files (recursive descent into `meta`, `moov`, `trak`, …), so its
first mutation starts inside a box body. Seeds are de-duplicated by SHA-1 and
reduced with libFuzzer `-merge=1`, which keeps only seeds that add coverage.

|---|---|---|
| `file_fuzzer` | 81 / 179 610 | 22 174 / 44 895 868 |
| `api_fuzzer` | 87 / 200 530 | 46 143 / 69 499 150 |
| `box_fuzzer` | 181 / 57 815 | 39 205 / 4 847 967 |
| `tile_fuzzer` | 88 / 204 139 | 19 662 / 29 659 811 |
| `sequence_fuzzer` | 37 / 76 011 | 35 577 / 39 355 915 |
| `color_conversion_fuzzer` | 4 / 31 612 | 2 146 / 2 805 533 |

## Campaign C (extended campaign, `harness/d3/campaign.py`)

Three self-contained phases of 5 400 s each, so that a runner timeout cannot
lose the whole campaign. The runner has 4 vCPUs and 15 GB; three workers, one
per target, leave one core for the niced coverage checkpoints and triage. (The
handoff rule `min(cores - 2, RAM_GB)` gives 2; three was chosen to use the
fourth core, and the measured CPU time below is the child CPU actually used.)
Flags are those of Campaign B except `-rss_limit_mb=1200`, `-max_len=65536`
and 900 s chunks (all recorded in each `campaign_summary.json`).

| Phase | Workers | Starting corpus |
|---|---|---|
| `long2a` | file, api, tile | Campaign B final corpus distilled with `-merge=1`, plus 400 generated seeds (`--seed 428`) |
| `long2b` | file, api, sequence | `long2a` live corpus, plus 300 generated seeds with region items and compressed metadata (`--seed 529 --features unc,regions,meta`) |
| `long2c` | tile, file, box | `long2b` live corpus; `box_fuzzer` from Campaign B's corpus distilled with `-merge=1` |

**Corpus distillation.** Campaign B's 164 907 final units were reduced per
target with `-merge=1` into the starting corpus (api 46 143 → 2 113, tile
19 662 → 1 688, sequence 35 577 → 1 571, file 22 174 → 1 450, box 39 205 →
1 841 units; logs in `results/long2{a,c}/corpus_distill/`). The merged sets keep
Campaign B's edge count (the merge reports api 9 972, file 9 212, tile 9 240,
sequence 7 889 and box 6 072 edges, against B's single-worker maxima of
9 969 / 9 156 / 9 184 / 7 745 / 6 091; the merge counts the seeds as well); the merge ran without `-use_value_profile`, so value-profile-only
inputs were dropped and rebuilt by the campaign. Campaign B's tarballs were
written on macOS and contain one AppleDouble `._<name>` file per unit; none of
them adds coverage, so none survived the merge, and `seed_gain.py` deletes them
before measuring.

**Structured seeds** (`harness/d3/gen_seeds.py`, new). `prepare_corpus.py` only
carves boxes out of the upstream fixtures, so mutations spend most of their
budget repairing a broken container. The generator writes complete files —
`ftyp`, `meta` (`hdlr`, `pitm`, `iinf`, `iloc`, `iprp`/`ipco`/`ipma`, `iref`)
and `mdat` with correct offsets — whose images are ISO/IEC 23001-17
uncompressed (`unci`) items. These decode without an external codec, so every
execution reaches pixel code. Randomised: the `uncC` component list (type, bit
depth, format, alignment), sampling, interleave, block and pixel size, row and
tile alignment, uncC tiling, `cmpd`, optional `cmpC` (zlib/deflate/brotli) and
`icef`; `ispe`, `pixi`, `irot`, `imir`, `clap`, `colr`; composition as a single
item, a grid whose tiles may differ in depth, sampling or size, an overlay, an
`iden` chain, thumbnails and alpha auxiliaries. Three quarters of the items are
drawn so that one of the seven unc decoder families accepts them; the rest are
unconstrained. The second batch adds `rgan` region items (all seven geometry
types, inline and referenced masks, truncated counts) and `mime`/`Exif`
metadata with `compress_zlib`, `deflate`, `br` and invalid encodings. Output is
deterministic from `--seed` (re-running `--seed 428` reproduces the 400
`long2a` files byte for byte) and each batch has a manifest
(`results/long2{a,b}/gen_seed_manifest.csv`). The decode checker
`harness/d3/tools/heif_check.cc` showed 116 of the first 400 seeds decode to
pixels and 151 of the 300 second-batch seeds carry at least one parsed region
item; none triggers ASan. Only generated files are used; no upstream
regression input is used or transformed.

**Harness fix.** `campaign.py`'s checkpoint thread called `proc.kill()` on a
finished `subprocess.run()` result at shutdown, which raised and ended the
thread; it now just stops. No measurement depended on it.

## Triage

`harness/d3/triage.py` replays every artifact once, extracts a signature
(sanitizer class plus the first three non-interceptor frames), and records the
wall time. Sanitizer crashes are minimised with `-minimize_crash=1` and must
reproduce the same signature three times. Out-of-memory reports cannot be
minimised by libFuzzer, so `harness/d3/minimize_oom.py` runs classic ddmin over
byte ranges, rewriting the outer box size at each step, and keeps an input as
long as the same failure still happens. Every causal claim was checked against
the source with `addr2line -f -C` on the addresses in the sanitizer report.

## Replay (before and after)

`harness/d3/replay.py` executes (a) every unit of the saved final corpus with
`-runs=0` and (b) every distinct crashing input with `-runs=1`, against a named
build directory. The command line, environment and inputs are identical for the
baseline and patched builds; only `--build` and `--label` change.

## Crashes found

| ID | Campaign | Target | Inputs | Original → minimized | Sanitizer | Classification |
|---|---|---|---|---|---|---|
| C1 | A | api, box, file, sequence, tile | 188 | 25 B → 8 B | UBSan nonnull (arg 1) | not exploitable |
| C2 | A | api | 31 | 813 B → 308 B | UBSan nonnull (arg 2) | not exploitable |
| R1 | B | box | 3 artifacts | 223 B → 45 B | libFuzzer OOM | denial of service |

| ID | Source line | Root cause |
|---|---|---|
| C1 | `bitstream.cc:115` | `StreamReader_memory::read()` calls `memcpy(data, &m_data[m_position], size)` with `data == nullptr` and `size == 0`. `Box_av1C::parse()` sizes an empty vector with `resize(0)` and passes `.data()` on; the wrong assumption is that a container's `data()` is always a valid `memcpy` destination, even for a zero-byte copy. |
| C2 | `heif_items.cc:170` | `heif_get_item_data()` calls `memcpy(*out_data, dataResult->data(), size)` for an item that exists but carries zero bytes. `data()` is `nullptr` for the empty result vector; the same wrong assumption on the source side. |
| R1 | `unc_boxes.cc:1365` | `Box_snuc::parse()` reads `image_width` and `image_height` from the box, computes `num_pixels = width*height`, calls `resize(num_pixels)` on two `float` vectors and then reads `num_pixels` floats twice. It never checks that the payload contains `8 * num_pixels` bytes, and the loop does not stop when the range is exhausted (`read_float32()` returns 0 and sets an error, the loop continues). The wrong assumption is that a header-declared element count is backed by bytes that are actually present. |

**C1 and C2 — why they are not exploitable.** `size` is exactly zero in both
reports: `memcpy` reads and writes no byte, and ASan reports no invalid access.
The abort comes only from `-fno-sanitize-recover`, which turns the UBSan nonnull
check into a trap. Replaying all 226 Part 1 artifacts in a release build
(libFuzzer only, no sanitizers) gives 0 aborts, and the patched build returns
exit code 0 on every one. The minimized C1 input is 8 bytes: `00 00 00 08 39 00 00 00`, a box
whose declared size is 8 and whose payload is empty.

**R1 — denial of service, with numbers.** The 223-byte artifact declares a
`snuc` box with `image_width = 25344` and `image_height = 10339`, i.e.
262 031 616 pixels, inside a `meta` box. `Box_snuc::parse()` then calls
`resize(262 031 616)` on a `float` vector, which is a single
`malloc(1 048 126 464)`. Under the campaign limit of 800 MB, libFuzzer aborts:

```
==8== ERROR: libFuzzer: out-of-memory (malloc(1048126464))
SUMMARY: libFuzzer: out-of-memory
```

With a 4 GB limit the same input parses to completion in **17.6 s** and
allocates about 2.1 GB (two `float` vectors of 1.05 GB). The minimal reproducer
produced by `harness/d3/minimize_oom.py` is 45 bytes:

```
0000002d 6d657461 00000000 00000021 736e7563 00000000
00000000 00 00006300 00002863 704e007f 7f7f7f7f 7f7f
```

It is a DoS, not memory corruption: the range reader checks bounds on every
`read32()`, returns 0 at end of range and sets `heif_error_Invalid_input`; ASan
and UBSan report no invalid access in a full run with a 4 GB limit; the only
observable effect is the allocation and the CPU time. The impact is real for a
photo service, and it does not need a sanitizer build: in a release build
(libFuzzer only, `-O2`, no ASan) the same 45-byte file takes **11.9 s and
2 048 MB peak RSS**, against **0.07 s and 47 MB** after the patch
(`results/baseline/rss_measure.csv`, measured with
`harness/d3/measure_rss.py`). The default limits do not prevent it, because
262 Mpixels is below `max_image_size_pixels` (32768²) and 2.1 GB is below
`max_total_memory` (4 GB).

The same `snuc`/`splz` code is unchanged in upstream master `12a259a5`
(26 October 2026): neither parser checks the remaining payload before sizing the
array. Because R1 is a denial of service and D1 defines a finding as a
memory-safety violation, it is outside the disclosure commitment in the D1
plan; the team reports it here and will send the reproducer to the maintainers
on request.

**Two slow-input classes that are not findings.** Campaign B also recorded two
`slow-unit` inputs (11 645 B and 12 834 B) and one 0-byte `oom` artifact. All
three were replayed on an otherwise idle machine: the slow units finish in
0.33 s, and the 0-byte artifact in 0.11 s with no error. Both slow units are
valid grid images that decode normally; they exceeded the 30 s wall-clock limit
only because twelve workers shared about four cores. The 0-byte artifact was
written while libFuzzer was loading a large corpus at startup (the OOM report
shows `MS: 0`, an empty base unit, and the allocation is ASan quarantine from
corpus loading). Neither is a libheif defect, and neither is counted as a
finding.

**Campaign C: no artifact of any kind.** In 13.841 CPU-hours and 115.7 M
executions the three phases wrote no crash, no OOM, no timeout and no slow-unit
artifact (`results/long2{a,b,c}/crashes.csv` are empty; `triage.py` reports
"0 artifacts, 0 distinct signatures" for each phase). There is therefore no C3
row. The goal of this revision — one reproducible, ASan-detected memory-safety
violation in the decode path — was **not reached**, and no impact is claimed.
Across Campaigns B and C, 25.1 CPU-hours and 203.8 M executions under ASan found
no out-of-bounds access, use-after-free or heap overflow. This is a null result
for the D1 property within the reached code; it is not evidence about the code
listed in the next section as unreached.

**Manual review alongside the campaign.** The decode-side code that the new
seeds reach was read for the invariant each write depends on. Each was found
enforced, which is consistent with the null result: the byte-align, block-pixel
and block-component unc decoders write at `(x0 + x) · bytes_per_sample` into
planes allocated from the same `uncC` component with the same rounding
(`pixelimage.cc` `ComponentStorage::alloc`, 1/2/4/8/16 bytes); per-tile chroma
extents use floor division so tiles never exceed the chroma plane
(`unc_decoder_legacybase.cc`); the single-tile path allocates a tile-sized image
and decodes at (0, 0) (`unc_codec.cc` `decode_uncompressed_image_tile`);
`BitReader::refill()` stops at the end of the data, so a short payload reads
zeros, not past the buffer; grid paste checks chroma and per-channel bit depth
before `memcpy` (`grid.cc`, `pixelimage.cc` `copy_image_to`); region masks
check the remaining data with 64-bit sizes before copying (`region.cc`); and
`saiz`/`saio` sample-info lookups are bounds-checked (`sequences/track.cc`).
This review is supporting context, not a proof of absence.

# Mitigation

The fix is in code, in two patches, and both are class fixes rather than
single-line patches.

Campaign C found no new failure class, so this revision adds no third patch;
M1 and M2 are unchanged, and Campaign C is their re-evaluation under a longer
campaign (see *Before and after*).

**M1 — zero-length buffer copies (`bitstream.cc`, `heif_items.cc`,
`heif_color.cc`, `hevc_boxes.cc`, `vvc_boxes.cc`, `context.cc`).** Every
`memcpy`/`memmove` that can receive a zero-length buffer now guards the call.
This removes the C1 and C2 classes at their call sites and brings every
remaining zero-length copy through these APIs to the standard that
`file.cc:1398` already uses in the pinned tree (`if (size > 0)`). It does not
change behaviour for non-zero lengths.

**M2 — declared element count versus payload size
(`codecs/uncompressed/unc_boxes.cc`).** Three parsers size an array from a
header field and then fill it by reading: `Box_cmpd`-style Bayer pattern pixels
(8 bytes per entry), `Box_splz` polarization angles (4 bytes), and `Box_snuc`
gain/offset arrays (8 bytes). Each now checks

```cpp
if (range.get_remaining_bytes() / bytes_per_element < num_pixels) {
  return {heif_error_Invalid_input, heif_suberror_Invalid_parameter_value, ...};
}
```

before any allocation, and the outer box size bounds the loop, so the parser
cannot allocate more than the input can justify. This covers the class "array
length taken from the header, filled from a shorter payload" for every
float-array box in the uncompressed codec, not only the `snuc` box that the
fuzzer found.
